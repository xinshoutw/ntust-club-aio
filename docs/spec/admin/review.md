# 活動申請審核

`/admin/review` · `admin` · 權限鍵 `areview` / `approve_advisor` / `approve_chief` / `approve_dean` · `features/admin/ReviewPage.tsx` + `ActivityReviewModal.tsx`

## 用途

活動申請的三關簽核(或無補助的單關)。學務長本人也走這頁。

## 資料來源

| 動作 | 端點 |
|---|---|
| 待審佇列 | `GET /admin/activities?status=…`(僅登入者可簽核的狀態) |
| 最近審核 | `GET /admin/activities?status&club_id&type&sort&page`(伺服器分頁) |
| 詳情 | `GET /admin/activities/{id}` |
| 核准 / 退回 | `POST /admin/activities/{id}/approve`、`/reject` |
| 社團選項 | `GET /admin/clubs/options` |

## 畫面

**待審佇列**(上)— 只列**本關**可簽核的單(側欄徽章算同一個集合):活動名 + 大型徽章、社團 · 類型 · 送件日、活動日期、擬請補助、「審核」鈕。早的在前(送件時間,**每次送審覆寫** —— 退回重送就是重新到承辦手上,D-29)。整批撈回(小結果集),分頁在前端切,每頁 8。

**最近審核**(下)— 表格依序:狀態、社團、活動名稱、類型(附大型徽章)、活動日期、擬請補助、審核時間。社團漏斗是二級選單(第一層=性質資料夾,`groupActiveClubs`;只列啟用中社團,見 `design-guide.md` §6)。狀態集合是**顯示狀態**(`features/activities/types.LISTED_STATUSES`,與社團端同一份),含推導的 `locked` —— 後端的 `approved` 篩的是畫面上的已核准、不含顯示為「已逾期」的那些,不明列 `locked` 的話逾期未結案的單會從這張表整批消失,而漏斗選項也是由這份推導的。社團/類型/狀態可多選篩選,社團/名稱/類型/日期/狀態/審核時間可多鍵排序,預設 `-reviewed_at`(無審核紀錄殿後)。伺服器端分頁,每頁 10。列表或社團選項任一失敗,表格內就改顯示失敗原因與重試鈕(不顯示「無符合篩選條件」——空結果與載不到是兩件事);已選社團而選項載不到時篩選一律 fail-closed 為空集。

**審核彈窗**(全站唯一那支 `ActivityReviewModal`:行政端四頁 —— 申請審核、結案審核、所有活動、社團活動列表 —— 加上社團端的活動列表;同一份版面,差別只在傳不傳簽核回呼與 `viewer`,見 D-34):

- **窗的大小固定成兩類**:有經費 1080、無經費 640,高度一律 `min(560px, 58vh)` 內容內捲。切頁籤、內容多寡都不改變它 —— 連著審一批單子時每一顆鈕都停在同一個位置
- **標題列的「申請 / 結案」撥桿**分流內容:申請側=基本資料 + 經費明細 + 申請的簽核紀錄;結案側=結案成果 + 活動照片 + 成果影片 + 學習心得 + 繳交確認 + 結案的簽核紀錄。結案側在**有結案資料、或有結案的簽核列**(逾期手動解鎖寫的就是這種)時才切得過去,否則反灰;**有結案資料時預設就開在結案側**(承辦那時要看的是結案),只有解鎖紀錄的單留在申請側
- 標題列:活動名、大型徽章、狀態 pill、右側**簽核章軌**(承 / 組 / 長 三顆章;無補助的單關不畫,`viewer="club"` 一律不畫)、關閉鈕左側的「⋯」下載選單(照片 zip、社團活動申請表 PDF;PDF 端點依 `viewer` 分社團端/行政端兩支)
- **蓋不蓋章看簽核紀錄,不看單據狀態**:狀態說「已核准」就把三顆章全點亮,等於替沒有簽核紀錄的組長與學務長背書 —— 舊系統遷入的 53 件已核准活動只留了 1–2 位簽核者。`status` 在章軌只回答「現在輪到誰」(`pending_*` / `rejected`);退回件標的是**第一個沒簽到的關**(組長退回時承辦人那關已經簽過了)(那一格寫「已退回」不是「等待中」—— 退回不是在等,是已經有結論了)。**還在跑的單子畫滿三格,已終結的只畫到最後一格有動作的關卡** ——核定 0 元即當場核准,後兩關永遠不會有人簽,標成「等待中」是等一件不會來的事
- **章軌的關卡數不固定**:核定 0 元即當場核准只畫一格、退回件兩格,連接線因此是**固定長度**、整條軌居中 —— 用 `flex:1` 撐滿固定寬會把少畫的那幾格拉成一條長虛線、章黏在盒子左緣
- **章下方那格是給簽核者的**:還沒簽到顯示「等待中」(關卡色),簽了才換成姓名,再下一行是簽核時間(`MM/DD HH:mm`,hover 出完整時刻)。印關卡名(承辦人 / 組長 / 學務長)會讓還沒簽的兩關看起來也有人經手 —— 關卡本身由章面的字表示。姓名與時間取詳情的 `stamps`(後端 `services.apply_approvals` 推導:**該關最後一次核准**)——退回重送後承辦人會再核一次,前端自己把核准列依序排會把第二次的承辦人印在「複核」
- 左:基本資料(社團(含類型,如「國際學生社 · 活動」)、**申請時間**、活動時間、活動地點、預期人數、**經費來源**、**活動內容、工作分配**、申請附件**點開站內預覽彈窗**,不另開分頁、檔名右側附**逐檔下載鈕**(預覽窗只給不能線上看的檔(zip、舊 .doc)下載入口,圖片與 PDF 走預覽分支,少了這顆就沒有地方把附件存下來)、**備註**(附件下方,多行輸入框));類型為「活動」時有「認可為大型活動」勾選框(`viewer="club"` 不畫 —— 那是承辦的決定,社團在標題徽章看結果)。工作分配與社團端詳情共用 `features/activities/WorkTable`(一行一列的項目 / 負責人,對齊規則同該元件)
- **簽核紀錄**(底部全寬):`approval_records` 逐列印**關卡、簽核者、時間、決議與退回原因**。**依 `subject_type` 分到兩側** —— 申請的簽核歸申請頁籤、結案的歸結案頁籤,列上因此不必再標一次「結案」。退回原因原本只有社團看得到,承辦要追得去翻稽核軌跡;每次送審不清簽核紀錄,退回重送後兩輪的核准與退回都還在。**結案退回連寫的那筆自動解鎖不單獨成列** —— `close_reject` 為了 D-05 先寫 UNLOCK 再寫 REJECT,而承辦人按的是「退回」,把自動解鎖印成一行讀起來像另外有人解鎖過這張單(摺疊在 `api/adminActivities.dropAutoUnlock`;手動解鎖後面不接退回,照樣印)。章軌只印**每一關最後一次核准**,退回與退回重送後再核的那幾次都不在軌上 —— 而「這張單被卡在哪」要看的正是那幾列
- 右(有經費才出現):逐項核定表(摘要 / 自籌 / 擬請 / 核定),底部合計**落在各自欄位正下方**(併格的話核定合計會壓在擬請欄上,對不回欄名)
- **沒申請補助就沒有東西可核**:整單擬請合計 0 時核定欄不出現、經費來源轉唯讀(後端同一條界線:擬請合計 0 帶非零核定回 422、經費來源在核定總額 0 元時不必填);逐列同理 —— 擬請 0 的那一列直接顯示 0,不給一個 `max=0` 永遠打不動的輸入框。**「能不能改」與「看不看得到」是兩個判定**:經費來源掛在基本資料而不是經費明細下,認定過的來源不論有沒有經費明細都印得出來
- 三個金額欄的寬度**由資料決定**(`types.numColWidth`:以最寬的一個數字為準):自籌/擬請各看自己的最大值,核定跟擬請同寬(核定 ≤ 擬請)再加輸入框的內距與邊框;其餘寬度全給摘要 —— 遷移進來的說明可以到數百字
- 兩塊的標題都用 `components/ui/SectionTitle`(標題 + 分隔線),與社團端詳情、結案審核同一支
- 底部:退回(必填原因的子彈窗)、核准。非本關時整個彈窗唯讀並說明原因。**結案側的底部另有「繳交確認」三個勾選框(靠左,與簽核鈕同一列)** —— 承辦是連著那兩顆鈕一起決定的;**已結案才顯示落庫值**,未簽核前一律走推導初值(三個旗標在簽核前是欄位預設的 true 佔位值)
- 詳情查詢失敗時內容整塊換成失敗原因與重試鈕(不留列表列那半份基本資料 —— 附件與經費逐項都不在,顯示成 `—` 看起來就像沒填),底部收掉退回與核准:讀不到逐項擬請就核准等於整單核定 0 元

## 規則

- **有核定補助**(逐項核定合計 >0):承辦人 → 組長 → 學務長;**核定合計 0 元**:當場核准,不論停在哪一關(D-16)。判準是核定不是擬請 —— 社團申請了、承辦人決定不給,一樣不必再送組長與學務長。逐項加總才是權威值:遷移件的 `activities.school_approved` 是 NULL,拿聚合欄位判會把「還沒補寫聚合值」讀成「核定 0 元」而跳過後兩關
- 經費來源、逐項核定、大型活動認可**只有第一關可編輯**,組長與學務長關唯讀核准
- **備註反過來:任一關都寫得動**(D-33)—— 那是留給社團看的話,不是第一關的認定,組長與學務長也留得下話。**空字串就是清空**:送出時不做 `trim() || null`,否則「清掉備註」這個動作按不掉。與經費來源一起印進申請表的意見回饋,社團端詳情也看得到,所以它是**寫給社團的**,不是承辦的內部註記
- **備註沒動過就不送**:種值取自**清單列**(詳情到位不重種),那份可能落後 —— 每一關都送的欄位一旦回寫舊值,就是把別人剛寫的備註靜靜蓋掉
- **寫入點只有「核准」那一按**:退回時輸入框裡的字不會送出(`RejectIn` 只收退回原因),核准後也沒有地方再改 —— 要改只能退回、等社團重送、再核一次(重送不清備註)。這一格會印在社團下載得到的正式申請表上,錯字目前沒有便宜的更正路徑
- 經費來源**預填「學務處補助」**(placeholder 同字):承辦人幾乎都填同一句。只在有申請補助且尚未認定過的單預填,而且**送出時看核定不看擬請**:核定 0 元(D-16)又沒被承辦人改過的那一格送原值,不送預填值 —— 那一欄會原樣印進申請表的意見回饋,沒動到學校的錢的單不該替承辦人寫上一句
- **每一項都要有核定金額**(擬請合計 >0 時;0 也是核定,`None` 是「還沒看」,兩者不能混),總額由後端加總寫入 `school_approved`。**經費來源只在核定總額 >0 時必填**(D-16)——整單核定 0 元沒有來源可認定,還逼承辦人填一句空話才存得下去。缺項的檢查必須排在總額判斷之前:有 `None` 就算不出總額。**核定 0 元的短路同樣要求逐項都核定過** —— 缺項守衛只在第一關,組長/學務長關拿到逐項 NULL 的遷移件,`or 0` 會把「還沒核定」讀成「不給」而跳過學務長
- **學務長關卡必須本人操作**:即使 `super` 也要明確持有 `approve_dean`,否則 403
- 大型活動認可:未申請也可由管理員逕行核定(勾選即 `is_large=true` + `is_large_approved=true`);已申請但不勾 → `is_large_approved=false`
- 退回原因必填,退回後狀態轉 `rejected`,社團可修改重送
- 受限關卡帳號的**視野也受限**:只看得到自己關卡相關的狀態,其他狀態的活動連詳情都回 404(避免探測)
- 每次核准/退回都寫 `approval_records` 與 `audit_logs`,並推 Discord

- **大型活動認可**:第一關是認定點(沒勾即否准),但**組長與學務長關仍改得動**(decisions.md ISS-54);後兩關省略該欄=不動,不會把已給的認可清掉
- **逐項核定不得高於該項擬請補助**(decisions.md D-03),超出回 422 `APPROVED_OVER_REQUESTED`
- **無補助案核不出金額**:擬請合計 0 時帶任何**非零**核定金額回 422(帶 0 等同不核),`school_approved` 一律寫 0 —— 單關核准的前提就是這張單不動到經費
- **相鄰關卡不得由同一人簽核**(`_require_different_actor`):同時持 `approve_advisor` + `approve_chief` 的帳號連按兩次會被擋在組長關,`super` 亦同。列鎖只擋得住同一關被重放,擋不住一路簽到底
- **退回件重送會作廢上一輪的核定**:社團不編輯直接重送也一樣,`submit` 會把逐項核定與 `school_approved` 都歸零 —— 彈窗的核定欄因此退回該項擬請金額(未核定時的預填值),而不是上一輪核過的數字
