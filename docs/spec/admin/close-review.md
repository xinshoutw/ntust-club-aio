# 結案審核

`/admin/close-review` · `admin` · 權限鍵 `aclose` / `approve_advisor` · `features/admin/CloseReviewPage.tsx`

## 用途

結案的承辦人單關審核,以及逾期未結案的解鎖。

## 資料來源

| 動作 | 端點 |
|---|---|
| 待審結案 | `GET /admin/activities?status=closing_pending_advisor&sort=-date` |
| 逾期未結案 | `GET /admin/activities?overdue=true&sort=date` |
| 詳情 | `GET /admin/activities/{id}` |
| 核准 / 退回 | `POST /admin/activities/{id}/close-approve`、`/close-reject` |
| 解鎖 | `POST /admin/activities/{id}/unlock`(需 `aclose`) |

## 畫面

**待審結案**(上)— 活動名、社團 · 活動日期、核定補助、「審核」鈕。伺服器分頁每頁 8。

**逾期未結案**(下,**持 `aclose` 或 `areview` 可見**)— 表格:社團、活動名稱、結案期限、狀態(已逾期 / 已解鎖)、動作(鎖定中出現「解鎖」)。逾期最久的在前,伺服器分頁每頁 10。點列開**唯讀**的活動詳情彈窗(重用 `ActivityReviewModal`)。這批全是 `approved`,只持 `approve_advisor` 的帳號看不到該狀態 —— 整段連同標題的件數一起收掉,送出去只會拿 403。**解鎖另外只認 `aclose`**,看得到不等於動得了。

**結案審核彈窗** — 社團、活動日期、實際時間/地點/人數、送件時間、經費(核定補助 · 自籌 · 實支;超出總經費時實支標紅)、成果(照片張數 · 影片連結 · 心得人數;照片 <5 張且無影片時紅字提示不計分)、活動重點 / 達成目標 / 其他成果 / 檢討會議、照片縮圖牆(點開原圖)、學習心得全文。

底部「繳交確認」三個勾選框(活動照片 / 成果報告表 / 學習心得),下方一行提示未達採計門檻者已自動取消勾選、核實無誤可自行勾回。動作:退回(必填原因)、核准結案。

詳情載入失敗時內容換成失敗原因與重試鈕,並收掉退回與核准 —— 看不到照片與心得就沒有東西可核實,而繳交確認也只會是空詳情推導出來的值。背景重抓失敗(手上已有詳情)不動內容,否則讀得到的單反而變成不能簽。**重抓期間核准鈕停用**:繳交確認是從手上這份詳情推導的,退回補件重送後,舊快取會把新繳的算成沒繳並永久落庫。

## 規則

- 分段標題(結案成果 / 活動照片 / 學習心得)用 `components/ui/SectionTitle`(標題 + 分隔線),與申請審核、社團端活動詳情同一支

- 結案是**承辦人單關**;核准後狀態轉 `closed`,退回則轉回 `approved` 讓社團補件重送
- 繳交確認寫進 `activity_reports.{photos,report,reflections}_confirmed`,`services/evaluation.py` 據此把未確認項目餵 0 給 `scoring.py`。三個旗標問的是**承辦認不認可採計**,不是「社團有沒有繳」
- **預設勾選由前端推導**(`features/admin/closeChecks.ts`):已落庫的旗標**且**內容達該旗標控制的評鑑門檻(ad2 照片 ≥5 張或有影片、ad3 報告表這一列存在、ad4 心得有上傳)才預設打勾。門檻取的是後端計不計分那條,不是結案送件的下限 —— 拿送件下限(照片 1 張、心得 3 篇)當門檻會把本來計得到的分數勾掉。核准是唯一寫得到這三欄的地方、寫完即 `closed`,一律預設全勾等於承辦沒動它就把遷移件帶來的「未繳」翻成「已繳」。推導只決定初值,承辦核實後自行勾回。**旗標是 AND 閘**:`evaluation.py` 要旗標為真**且**內容存在才計分,遷移件沒有搬照片與心得,那兩項勾回去也不會加分 —— 實質有效的只有成果報告表(ad3 只看那一列在不在)
- `CloseApproveIn` 的三個旗標與 `body` 本身都是必填,直呼 API 繞不過這個確認動作;詳情端點會帶出三個已落庫的旗標供前端推導(社團端共用同一支 `ReportOut`,也看得到自己的)
- 解鎖只對「已核准 + 已逾期鎖定」的活動有效;**未逾期不得預先解鎖**,否則等於永久繞過鎖定
- **退回結案即自動解鎖**(decisions.md D-05):結案已在期限內送到,補件往返不該再被期限擋下。該活動仍在逾期清單裡,只是狀態顯示「已解鎖」、沒有解鎖鈕。自動解鎖會寫 `activity_close_unlocked` 稽核與一筆 `UNLOCK` 簽核紀錄 —— 「這張單是誰解的鎖」要查得到
- **解鎖是永久的**:`close_unlocked` 沒有任何地方會設回 false,也就是說被退回過一次的結案從此不受期限約束。仍列在逾期清單裡供承辦追蹤,但期限本身對它不再生效
- 兩張表的頁碼只在查詢成功後跟著總數收斂:失敗時 `total` 會塌成 0,一起 clamp 會把錯誤說明與重試鈕洗掉
- 逾期清單 `overdue=true` 含已鎖定與已解鎖兩種,由回應的 `close_locked` 區分
- 逾期清單在 DB 端篩(`activity_service.close_overdue_sql`),與 `is_close_locked` 共用同一條期限與 `close_lock_days`

- **`aclose` 涵蓋核准與退回**(decisions.md D-08):能看就能簽,不必另持 `approve_advisor`
- 「逾期未結案」全是 `approved` 狀態:看不到該狀態的帳號查詢直接回 403,**不給一個假的 0 件**
