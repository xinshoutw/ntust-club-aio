# 可改進方向

系統可用之後仍可再往前走的方向。**這裡不是待辦清單**,不排期、不承諾;
必須完成的項目在 [`issues.md`](issues.md) 與 [`gaps.md`](gaps.md),已定案的規則在 [`decisions.md`](decisions.md)。

每一項都附「現在是怎麼運作的」,因為改進的價值取決於現況能撐到哪裡。

---

## 1. 功能延伸

**三支腳本用行程本地日期推學期**
`scripts/seed_mock.py`(mock 固定借用可能落到前一學期)、`migration/set_contact_emails.py`
(學期邊界會錯分「位址應可用/可能畢業」兩組,實際寫入的名單不變)、`migration/cms_import.py`
(只影響輸出檔名)。正式映像與 compose 都沒有設定行程 TZ。

**器材個體追蹤**
系統目前不記錄器材序號。標記為「依序點交」的品項只會在點交畫面提醒工讀生現場核對,
核對結果不入系統,因此無從得知某一台機器現在在誰手上。
若建立器材個體主檔(一台實體機一列),點交改為從清單勾選,借用紀錄就能追蹤到單一機器,
也自然得到「同一台不會同時掛在兩張單上」的保證,並可再延伸出維修與報廢的生命週期。
需要先盤點每一台的實際序號。

**社團導覽首頁**
現在 `/` 直接是登入頁。導覽頁可展示所有社團、社團圖片與簡介,登入入口收到右上角。

**公開頁**
舊系統有數個免登入即可瀏覽的頁面,新系統目前全部需要登入。

**統計與匯出**
社團活動統計、競賽資料完成度、經費稽核明細與 xlsx 匯出。
現有的四支 CSV 匯出(稽核、行政成員列表、報名管理、社團成員列表)已涵蓋逐筆資料,但沒有跨社團、跨學期的彙總視角。

**待審佇列的自動化**
待審申請目前一律人工處理,沒有逾時自動駁回;固定借用衝突時承辦需逐單開視窗,
沒有批次核准或衝突連鎖駁回。申請量成長後這兩處的承辦工時會線性增加。
(GAP-12 / GAP-13 已定案維持人工,列在這裡是備而不用。)

**評鑑相關的維護介面**
以下欄位系統讀得到、但沒有任何地方寫得進去,目前只能直接操作資料庫:
評鑑上傳鎖與評語公布(`eval_settings`)、逐年 rubric 與獎項主檔(換學年時需調整程式)。
檔案歸檔(`files.archived_at`)也在此列,但 decisions.md GAP-08 已定案由 infra 處理、系統不做介面。

**評分草稿跨裝置**
評審評分目前只存在瀏覽器的元件狀態,關閉視窗即失。改為後端暫存可跨裝置接續。

**建立之後就改不動的幾張單**
以下都是「建錯只能重來或動 DB」:場地不開放規則不可編輯(只能刪掉重建)、
行政手動借用建立後不可修改(撤銷要繞到借用管理的審核彈窗,手動借用頁自己沒有入口)、報名活動沒有刪除端點、公告發布後內容與對象不可改、
幹部證明與郵局異動與報修的狀態不可回退(誤按「處理中」沒有回頭路)。
每一項單獨看都不大,合起來是承辦最常抱怨的一類。逐頁細節見各自的 spec。

**幾處「資料還在但沒人看」的殘值**
社團編輯退回件時 `school_approved` 不會同步清除(只有重新送出那條路徑會清),
DB 裡因此留著上一輪的核定總額;目前沒有任何畫面讀它(前端一律由逐項核定加總),
所以看不出異常,但這種殘值遲早會被新功能誤用。
歸還點交頁同樣拿得到聯絡電話卻沒有渲染,而借出點交與逾期追蹤都有。

**行政端補開違規單**
違規勸導目前只能由工讀生端開立,行政端看得到、改得了狀態,但補不了單。

**報名表單的自訂欄位編輯**
端點支援零報名時修改 `fields`,但沒有 UI —— 要回到 builder 那種拖曳排序的介面才好用。
另外 builder 沒有未存檔守衛,也不能存草稿。

**Telegram Bot 通知**
現有通知走 Discord webhook 與 Email 兩條路徑,可再擴一條。

**舊系統歷史資料**
舊評鑑檔案庫(12,752 檔 / 14 分類)已定案不遷(MIG-08);行政歷史文件待決(MIG-10)。

## 2. 效能與規模

**上傳改串流處理**
大小上限已由前面的網頁伺服器逐端點擋下,但應用層仍是 multipart 整包先落到暫存目錄
再逐塊寫盤與計算雜湊,而且寫盤與雜湊在 async 端點內同步執行。
改為邊收邊處理、並把雜湊移出事件迴圈,可讓超大檔在讀完之前就中止,
暫存空間的峰值需求與併發上傳期間的延遲都會下降。

**磁碟配額預留**
容量檢查目前是上傳前的前置閘。改為「開始上傳時先預留、結束時結算」可完全消除同時上傳的競態。

**檔案改物件儲存**
上傳檔案現在放在主機磁碟。改放物件儲存後,容量、備份與多機部署都不再受單機限制。

**通知投遞落地佇列**
通知是交易提交後的背景投遞,失敗時做記憶體重試並記錄。
改為落地佇列表後,重試狀態可在程序重啟後續存,也能看得到投遞歷史。

**限流狀態共用**
登入限流是行程內記憶體計數,單機運作正常,重啟後歸零。
多機部署時需改為共用儲存,否則各機各算一份。

**幾處缺索引的查詢**
稽核的 `role` / `action` 篩選與 `/options` 的 `DISTINCT action` 都是整表掃描;
檔案管理的模組篩選與大小排序同樣沒有對應索引。現行資料量下都還不痛。

**行政待審列表的可借數逐列查詢**
社團端借用頁已改成一次 GROUP BY 算完整份主檔,行政端待審列表仍逐列查
(每列的日期區間不同,不能共用一份),受分頁上限保護。

**全文檢索**
活動、公告與社團目前是欄位比對查詢。資料量成長後可考慮引入全文索引。

## 3. 可靠性與維運

**服務健康檢查**
`compose.yml` 目前只有資料庫有 healthcheck,網頁層對後端也沒有等待條件。
啟動瞬間可能出現短暫 502(內層 nginx 會自行恢復,不會卡死)。

**log 輪替與保留**
尚未規劃。磁碟水位有 `check_disk.py`、後端存活有 Uptime Kuma 心跳,兩者都只差部署層掛上。

**開機請求的逾時**
前端開機時會確認登入狀態,該請求目前沒有設定逾時。
後端連得上但不回應時,畫面會等到反向代理逾時才顯示錯誤。

**過期 session 清理**
目前於使用者登入時順手清除,沒有獨立排程。長期無人登入的時段不會清理。

**內網信任範圍**
內層 nginx 目前信任所有私有網段,實際邊界依賴雲端防火牆。可收窄至實際來源。

**異地備份**
現行備份與服務位於同一環境,可防誤刪與系統錯誤。異地副本可再涵蓋環境整體損失的情境。

## 4. 測試與品質

**尚未涵蓋的測試類型**
真實併發、權限矩陣、月底與閏年與時區邊界、檔案系統故障。

**兩個已知需要重寫的既有測試**
一個是假併發(兩支請求會自己排成序列,拿掉鎖照樣通過),一個名實不符。
(第三個原本相依於執行機器的時區,已由 `tests/conftest.py` 固定台北時區 + 該測試開頭的
時區斷言收住。斷言是為了讓「有人拿掉那兩行」立刻紅 —— 少了它,錯誤時區每天仍有約 16 小時
會矇混過關。測試本身仍以 `date.today()` 為基準,要完全不依賴當下日期得改成可注入的今天。)

**端對端測試**
目前沒有 E2E。若要建立,必須打網頁容器的對外埠,
直接打後端埠會繞過上傳上限、登入限流與安全標頭。

## 5. 使用體驗

**前端的日界判定用瀏覽器本地時區**
`lib/semester.ts` 的當前學期、`lib/periods.ts` 的「節次是否已開始」、`lib/status.ts` 的停權判定
都以瀏覽器本地日期為準,後端一律走台北。不在 +08:00 的使用者在跨日的那幾小時會與後端不一致
(例如 7/31 傍晚,UTC 瀏覽器仍算上學年、後端已跳下學年)。
現有測試在任何時區都全綠 —— 因為測試資料也用同一個本地時區建立,測不出這件事。

**多語系**
現行僅繁體中文。舊系統為中英雙語。

**行動裝置的時段選取**
時段表在手機上維持逐格點選。批量拖曳選取與橫向捲動在觸控上無法並存,
目前優先保留捲動。若改用長按進入選取模式可兩者兼得。

**通知鈴鐺的覆蓋範圍**
社團端的鈴鐺已有內容,行政、工讀生與評審端目前恆為空。

**清單頁的篩選入口**
後端已支援但畫面沒有入口的:幹部證明 / 郵局異動 / 維修管理的 `club_id`,違規管理的社團與地點與日期區間。
另有幾張清單只有分頁沒有篩選:器材借出點交、社團端報名列表、行政端報名管理、
工讀生端違規紀錄(「社團」欄還不在排序白名單內)。

**檔案預覽格式**
瀏覽器可原生預覽的類型直接內嵌,其餘一律下載。可再擴充可預覽的格式。

**固定場地借用審核看不到同格的臨時申請**
`/admin/bookings` 的色格圖會把該格全部待審單標出來(含待審的固定借用),但真正審固定借用的
`/admin/rooms`(權限鍵 `aroom`)沒有這張圖 —— `aroom` 承辦核准固定借用時,看不到同一格底下
壓著哪些臨時申請。要做就是 `_sees_pending` 放寬成 `abooking or aroom`,並在該頁掛一張圖。
